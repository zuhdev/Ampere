The problem

Gas is where BOT Chain apps lose their users

Before a new user can do anything in your app, they are asked to acquire BOT first — find a faucet, wait, bridge, then approve a fee they do not understand. Every insufficient funds for gas error is a user you already paid to acquire, and then watched walk away.

Ampere removes that step. The app declares one rule — which contracts it will pay for, a cap per user, a budget per day — and the paymaster covers the gas on every eligible transaction. Users and agents sign normally and pay 0 BOT.

  • No faucet dependency for first-time users
  • No wallet pop-up asking for a fee the user cannot pay
  • Works for humans and autonomous agents from the same rule

Why plain wallets stall on BOT Chain

  • ✕
    eth_feeHistory returns a zero base fee

    EIP-1559 fee estimation collapses, so wallets that derive fees from history send nothing.

  • ✕
    eth_estimateGas is unreliable

    Auto-estimated limits under-price writes, and a wrong limit means a reverted, wasted send.

  • ✕
    New accounts start at 0 BOT

    The very first action is impossible without an external token transfer.

  • ✓
    Ampere pins the fee and the limit

    The relay reads eth_gasPrice, sets an explicit gas price and gas limit, then submits — the calibration is documented and covered by gastrace.

How it works

Four steps, one of them on-chain

The API is convenience and telemetry. Every limit that matters is enforced by the contracts.

  1. 1

    User signs

    The wallet signs the intent exactly as it normally would. No BOT balance, no fee prompt.

  2. 2

    API pre-checks

    Policy read, budget preview and rate limit in milliseconds — fast feedback, never the source of truth.

  3. 3

    Relay submits

    One signer, nonces serialized through a queue, 3 attempts with 1s → 2s → 4s backoff. Reverts are never retried.

  4. 4

    Paymaster pays

    isSponsorable() gates the call on-chain, measured gas is charged against the budget, the rest is refunded.

The rule

The policy lives on-chain, not in your server

Caps, allowlists, expiry and pause are evaluated inside isSponsorable() — the exact call the paymaster makes before it pays. The API can be bypassed, rate limits can be dodged, a server can be compromised; none of that overspends a single extra wei.

  • AllowlistTarget contracts only — empty list is deny-all.
  • BlocklistHard excludes, checked before the allowlist.
  • Per-address capRolling 24h ceiling per beneficiary.
  • Daily budgetWhole-app ceiling, resets 00:00 UTC.
  • ExpiryUnix timestamp — campaigns can end themselves.
  • PauseOwner-only kill switch, one transaction.

Developers

Gasless in four lines

One SDK for your app, one library for governance, plain HTTP for everything else.

@ampere/sdk 
import { Ampere } from "@ampere/sdk";

const ampere = new Ampere({ appKey: process.env.AMPERE_KEY });

// 1. ask first — reads the on-chain policy, sends nothing
const { sponsorable, gasCost, budgetRemaining } = await ampere.simulate({ to, data });

// 2. execute — Ampere relays it and pays the gas
const { tx, status, gasUsed, explorer } = await ampere.execute({
  to,
  data,
  beneficiary: user.address,
});

// 3. telemetry for your dashboard
const { relayed, failed, budgetUsed } = await ampere.usage();

// helper: send an ERC-20 transfer with 0 BOT
const data = Ampere.erc20Transfer(token, to, amount);
@ampere/relay/client 
import { setPolicy, depositNative, readPolicy } from "@ampere/relay/client";
import { keccak256, toHex, parseEther } from "viem";

const appKey = keccak256(toHex("ampere.demo"));

// declare the rule — written straight to SponsorPolicyRegistry
await setPolicy(appKey, {
  allowlist: [COUNTER],                    // only these targets get paid for
  blocklist: [],
  perAddressCap: parseEther("0.05"),       // per beneficiary, rolling 24h
  dailyBudget: parseEther("200"),          // resets 00:00 UTC
  expiresAt: 0n,                           // 0 = never expires
  paused: false,
});

// fund the escrow the paymaster draws from
await depositNative(appKey, parseEther("50"));

console.log(await readPolicy(appKey));

Security

Invariants, not intentions

What the system guarantees even when everything around it misbehaves.

01

No user custody

The vault holds sponsorship budget only. withdraw is owner-only; user funds never touch it.

02

Enforcement on-chain

Caps, allowlist, expiry and pause are checked by isSponsorable() and the paymaster — not by the API.

03

Empty allowlist = deny-all

A freshly created or misconfigured policy sponsors nothing until a target is explicitly added.

04

Reentrancy discipline

nonReentrant on state-mutating methods, state updated before external transfers, pause is owner-only.

05

Authenticated admin

Admin routes require x-ampere-key; per-appKey ownership is sha256(key) in the store.

06

Bounded throughput

Rate limit per appKey — 30 relays/min by default — plus a single serialized relayer nonce to avoid races.
